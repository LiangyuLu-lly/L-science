# L-science 平台需求文档

## Introduction

L-science 是运行在 Windows 上的本地优先 AI 科研工作台，面向以论文产出为终点的科研工作流。它对标 Anthropic 的 Claude Science（需求基线来自对其 `linux-x64` 单文件可执行程序的逆向分析），并在**多模型能力路由**这一维度上做出实质超越。

本文档定义 M0-M5 全部分期所需的功能与非功能需求。设计与技术决策见同目录 `design.md`；本文档只描述「系统必须做到什么」与「怎么验收」，不重复技术方案。

### 范围声明

**在范围内**：会话与项目管理、Jupyter 内核执行面（Python / R）、Shell 执行、沙箱与访问边界、Artifact 存储与血缘、多模型路由与降级、供应商适配与凭据、技能系统、计划与子 agent 委派、Reviewer 与 findings、文献库与 Claim Ledger 与手稿编译、MCP 连接器、远程算力、记忆、审批交互、成本可观测性。

**明确不在范围内**（已由用户决定取消或推迟）：

- 匿名化 / 脱敏引擎（检测器栈、Entity Vault、假名化、Leak Canary、哈希链审计、数据分级强制约束）。保留供应商策略标签作为**可选**路由过滤条件与一条普通出站日志。
- 多用户 / 团队协作 / 服务端部署
- 移动端或 Web 托管形态
- 模型训练或微调
- 湿实验设备控制

**已知取舍（用户知情）**：取消匿名化后，未发表手稿与受试者数据与普通文本走同一条出网路径，平台层面不做任何内容拦截。数据保护责任回到用户的会话级判断（选择本地模型或不粘贴敏感内容）。

### 术语

| 术语 | 含义 |
| --- | --- |
| 控制平面 | 独立于 UI 进程运行的后端，持有编排器、工具注册表、数据库与模型出口 |
| 执行平面 | 实际跑用户代码的地方：Jupyter 内核、Shell、远程算力 |
| Artifact | 被提升为受管产物的工作区文件，内容寻址存储且带版本谱系 |
| 血缘（lineage） | Artifact 版本之间的派生关系，以及版本与生成它的代码/输入版本的绑定 |
| 技能（Skill） | 按需加载的领域指令包，含 `SKILL.md` 与结构化清单 |
| Finding | Reviewer 提出的审查发现，分 WARN 与 FAIL 两级 |
| Claim | 手稿中一条可核查断言，必须绑定证据 |
| 托管环境 | 平台自己创建并管理的 conda 环境，与用户既有研究环境隔离 |
| 隔离徽章 | UI 上持续展示的当前沙箱后端隔离强度指示 |
| 硬过滤 | 路由第一阶段，按能力与合规性剔除不可用模型，结果为空时不降级 |
| Committee | 同一任务交给多家供应商的模型独立作答并交叉比对 |
| Escalation | 先用廉价模型批量处理，仅对低置信样本升级到高能力模型 |

## Requirements

### 需求 1：项目与会话管理

**User Story:** 作为研究者，我要把不同课题的工作分隔在不同项目里，每个项目下能开多个会话，这样上下文与产物不会互相污染。

#### Acceptance Criteria

1. 系统应支持创建、重命名、归档与删除项目，每个项目拥有独立的数据库、Artifact 存储与内核工作区。
2. 当用户在项目内新建会话时，系统应为该会话分配独立的工作区子目录，并继承项目级设置与记忆。
3. 系统应持久化会话的完整消息序列，包含每条助手消息实际使用的模型标识与 token 用量。
4. 当应用重启后，系统应完整恢复所有项目与会话的历史，包括未完成的后台任务状态。
5. 若删除项目，则系统应在同一事务内清理该项目的数据库记录，并在确认后回收不再被引用的 Artifact blob。
6. 系统应支持会话内中断当前轮次，中断后已产生的工作区文件与已保存的 Artifact 应完整保留。

---

### 需求 2：环境探测与诚实降级

**User Story:** 作为研究者，我要清楚知道平台当前实际具备哪些能力、缺什么、保护强度如何，而不是等到跑一半才发现环境不对。

#### Acceptance Criteria

1. 系统应在启动时探测运行时能力矩阵：Node 版本与 ABI、原生模块可加载性、conda 与托管环境、托管环境内的关键包、R 可用性、WSL2 发行版、Docker daemon、GPU、磁盘余量、进程是否提权。
2. 系统应提供命令行自检入口，同时输出人类可读报告与机器可读 JSON。
3. 当探测结果显示原生模块无法加载或托管环境缺少 `ipykernel` 时，系统应将其报告为阻塞项并以非零状态退出。
4. 若 R 运行时不可用，则系统不应注册 `r` 工具，且当用户或 agent 请求 R 能力时应给出可执行的安装指引而非模糊报错。
5. 系统应在 UI 上持续展示当前沙箱后端的隔离徽章，并原文展示该后端的全部已知缺口，不得省略或美化。
6. 当强隔离后端不可用而降级到弱隔离后端时，系统应显式告知用户实际保护强度的变化。
7. 系统应校验托管环境内 numba 与 numpy 的版本兼容性，并在不兼容时报告为阻塞项。

---

### 需求 3：Python 与 R 执行面

**User Story:** 作为研究者，我要在会话里直接跑分析代码，变量与导入跨调用保留，图表和表格能直接呈现在对话里。

#### Acceptance Criteria

1. 系统应通过标准 Jupyter 消息协议与内核通信，内核为上游 `ipykernel`（Python）与 `IRkernel`（R），不自研内核宿主。
2. 系统应对每条发出的内核消息按 Jupyter 规范计算 HMAC-SHA256 签名，签名段的拼接顺序为 header、parent_header、metadata、content。
3. 系统应将内核的 5 个通道全部绑定在回环地址，不得监听对外可达地址。
4. 当收到 iopub 消息时，系统应按 `parent_header.msg_id` 将其关联到发起的请求，不得按到达顺序推断归属。
5. 系统应在内核初始化序列中启用 inline 绘图后端，使 matplotlib 图形以 `image/png` 形式返回。
6. 系统应正确呈现多 MIME 富输出，至少覆盖 `text/plain`、`text/html`（DataFrame 表格）与 `image/png`。
7. 在同一请求内连续执行多个代码单元时，系统应保持变量、导入与函数定义的状态。
8. 当代码抛出异常时，系统应以结构化形式返回异常类型、消息与 traceback，而非仅作为 stderr 文本。
9. 当用户请求中断时，系统应通过 control 通道发送 `interrupt_request`；若内核在超时内无响应，则系统应重启内核。
10. 若内核进程崩溃，则系统应通过心跳通道检测到、自动重建内核、保留工作区文件，并明确告知用户内存状态已丢失。
11. 系统应支持将长时间运行的执行标记为后台任务，用户可继续其他工作，结果在完成时自动投递回会话。
12. 系统应支持补全与对象内省请求，为后续编辑器体验预留能力。

### 需求 4：Shell 执行

**User Story:** 作为研究者，我要执行命令行工具（装包、跑脚本、处理文件），并且在 Windows 上不必自己纠结 shell 差异。

#### Acceptance Criteria

1. 系统应提供无状态的 shell 执行工具，每次调用相互独立。
2. 在 Windows 上系统应默认使用 PowerShell；当 WSL2 发行版可用时，系统应允许调用方显式选择 bash。
3. 系统应支持后台执行长命令，并对输出量设置上限，超限时截断且明确标注已截断。
4. 系统应将 shell 的工作目录限制在项目工作区或已授权的宿主路径内。
5. 当命令以非零码退出时，系统应同时返回退出码、stdout 与 stderr，不得只报告失败。

---

### 需求 5：沙箱与访问边界

**User Story:** 作为研究者，我要确保 agent 生成的代码不会误改我系统里的重要文件或偷偷访问网络。

#### Acceptance Criteria

1. 系统应通过统一的沙箱后端接口支持三种实现：`native`、`wsl2`、`docker`，并在运行时按可用性选择。
   **本产品线不做：** `docker` 未实现，也不会做。实际后端是 `native`（Windows 作业对象）与 `wsl2`。隔离徽章的 skipped 清单与 UI 文案会说明这一点。
2. 系统应对内核与 shell 进程施加资源上限（内存、CPU、墙钟），并在控制平面退出时终止全部子进程，不留孤儿。
3. 系统应对所有文件路径参数做规范化校验，拒绝 `..` 穿越、符号链接与 junction 逃逸、UNC 路径、备用数据流以及大小写混淆。
4. 系统应拒绝对受保护路径的写入，至少覆盖 `.ssh`、`.git/config`、`.git/hooks`、`.vscode`、`.idea`、PowerShell profile 以及平台自身数据目录。
5. 当 agent 需要访问项目工作区之外的宿主路径时，系统应要求用户显式授权，并区分只读与读写两种模式。
6. 系统应支持查询与撤销已授予的宿主路径权限。
7. 若授权为只读，则系统应拒绝一切写入尝试。
8. 系统应按域名白名单管控执行平面的网络出口，并在 `native` 后端下明确告知用户该管控为代理级、可被绕过。
9. 当 agent 请求访问白名单之外的域名时，系统应发起用户审批而非静默放行或静默拒绝。

### 需求 6：Artifact 存储与血缘

**User Story:** 作为研究者，我要每一张图、每一份结果都能追回到产生它的代码与输入数据版本，否则论文里的数字我不敢用。

#### Acceptance Criteria

1. 系统应以内容寻址方式（sha256）存储 Artifact 二进制，相同内容不重复占用空间。
2. 系统应为每个 Artifact 维护版本序列，更新时创建新版本而非覆盖旧版本。
3. 当从工作区提升文件为 Artifact 时，系统应记录生成它的工具调用、语言与抽取出的代码血缘。
4. 系统应记录 Artifact 版本之间的派生关系，使任一版本都能向上追溯到其输入版本。
5. 系统应支持在代码中用 `{{artifact:VERSION_ID}}` 标记引用 Artifact，并在执行时解析为物理文件路径。
6. 系统应要求图像类 Artifact 具备可复现血缘（生成代码 + 输入版本），缺失时由 Reviewer 提出发现。
7. 当 agent 请求删除 Artifact 时，系统应阻塞在用户审批卡片上，列出待删条目；用户拒绝后不得重试同一请求。
8. 系统应支持按 version_id 或绝对路径读取文件；对 PDF 应支持按页读取以控制 token 消耗。
9. 若读取的是二进制格式（压缩包、音视频、HDF5、Excel），则系统应拒绝直接读取并提示改用代码工具处理。

### 需求 7：多模型能力路由

**User Story:** 作为研究者，我要平台按任务性质自动挑最合适的模型——筛文献用便宜的、写手稿用文笔好的、核引文用可靠的——而不是所有事都用同一个模型。

#### Acceptance Criteria

1. 系统应为每个模型维护能力向量，涵盖上下文窗口、最大输出、模态、十项能力评分、价格、延迟、供应商策略与本地标识。
2. 系统应支持按任务类型选择权重预设，任务类型至少覆盖设计文档列出的十三种。
3. 系统应在路由第一阶段执行硬过滤：模态支持、上下文窗口足够（含预留输出）、工具调用支持、健康检查通过、速率余量充足、未被用户禁用、凭据存在。
4. 若硬过滤后候选为空，则系统应向用户报告缺少哪些条件，不得放宽约束或静默降级。
5. 系统应按加权能力得分减去归一化成本与延迟惩罚，再加经验修正项进行打分排序。
6. 系统应记录每次路由决策的候选集、得分构成、被排除模型及排除原因，并在 UI 上以可解释形式展示。
7. 当被选中的模型请求失败（限流、服务端错误、超时、工具调用格式崩坏）时，系统应按得分降序跨供应商重试，并将重试关联到原决策。
8. 若失败原因是内容安全拒答，则系统应将其视为安全边界，不得更换提示词重试，也不得更换模型绕过。
9. 系统应支持 committee 模式：同一任务交给指定数量的不同供应商模型独立作答，交叉比对后将分歧显式上报给用户，不做静默多数表决。
   **本产品线不做：** 发送路径不跑委员会。`selectCommittee` 仅给路由预览列候选；UI 写明「发送只会跑主模型，不会自动连发」。
10. 系统应支持 escalation 模式：先用最廉价（优先本地）模型批量处理，仅对置信度低于阈值的样本升级。
   **本产品线不做：** `planEscalation` 不在发送路径上调用。发送只跑主模型，失败后走降级链。
11. 系统应从用户反馈（接受、重试、编辑量）、Reviewer findings 数量与严重度、工具调用失败率中提取奖励信号，用于修正经验项。
12. 系统应保证经验修正采用带探索的策略，不因早期少量样本而永久锁定某个模型。
13. 当会话开启「要求供应商承诺不用于训练」时，系统应将策略标签不满足的模型纳入硬过滤剔除范围。
14. 系统应允许用户覆盖任务类型的权重预设，并允许为单次请求强制指定模型。

### 需求 8：供应商适配与凭据

**User Story:** 作为研究者，我要能接入我实际拥有的各家模型 API，包括本地跑的模型，且密钥不以明文散落在磁盘上。

#### Acceptance Criteria

1. 系统应通过统一适配器接口接入供应商，新增一家不需要修改路由逻辑。
2. 系统应将各家的响应归一化为统一的增量流，至少区分文本、思考过程、工具调用与结束事件。
3. 系统应归一化停止原因，并将内容安全拒答与其他原因区分开。
4. 系统应支持本地模型端点（Ollama / vLLM 等 OpenAI 兼容接口）作为一等供应商。
5. 系统应将 API 凭据加密存储，Windows 上以 DPAPI 保护并绑定当前用户账户。
6. 系统不应在日志、错误消息、路由决策记录或 UI 中回显凭据明文。
7. 系统应提供不产生计费的轻量健康检查，用于路由硬过滤。
8. 当供应商返回可枚举的模型列表时，系统应支持自动发现并填充注册表。
9. 若凭据缺失或失效，则系统应将该供应商的模型从候选集剔除并在 UI 中标注原因。

### 需求 9：技能系统

**User Story:** 作为研究者，我要平台在需要时自动调用领域方法（睡眠分期、频谱分析、统计规范、期刊格式），而不是每次都由我口述流程。

#### Acceptance Criteria

1. 系统应按约定目录结构加载技能，包含主指令文档与结构化清单。
2. 系统应支持内置技能与用户自建技能两个作用域，用户技能可覆盖同名内置技能。
3. 系统不应将全部技能常驻上下文，而应按需检索并注入。
4. 系统应提供语义检索入口，检索索引在本地构建与查询。
5. 当技能命中后，系统应注入其主指令文档，并允许按需二次加载引用材料。
6. 系统应在技能清单中声明环境、包与连接器依赖，并在依赖缺失时给出可执行的补齐指引。
7. 系统应内置覆盖睡眠/生理信号/神经科学与通用论文写作的技能目录，具体清单见设计文档。
8. 系统应记录每个会话加载过哪些技能及加载原因，供用户审查。

### 需求 10：计划与子 agent 委派

**User Story:** 作为研究者，我给出一个较大的研究目标，我要平台先给出可审阅的执行计划，再分工执行，而不是一头扎进去乱做。

#### Acceptance Criteria

1. 系统应支持在执行前生成结构化执行计划，计划按阶段组织且每步可绑定技能。
2. 系统应要求计划生成发生在技能检索确认能力覆盖之后，每一步都落在真实存在的能力上。
3. 系统应在计划步骤中避免硬编码可检索得到的领域数值，若存在检索途径则应将检索本身作为一步。
4. 系统应在 UI 上展示计划与各步实时状态，并允许用户在执行前修改或拒绝计划。
5. 系统应支持将计划中的步骤委派给子 agent 并行执行，并支持向运行中的子 agent 发送引导消息或将其停止。
6. 系统应保证协调 agent 与子 agent 之间的产物通过 Artifact 或文件交接，而非依赖共享内存。
7. 当用户中断时，系统应取消由阻塞式委派产生的在途子 agent；显式声明为非阻塞的子 agent 不受影响。
8. 系统应对控制面 REPL 内核施加单例约束，并提供不共享状态的临时旁路内核以避免排队死锁。

### 需求 11：Reviewer 与 findings

**User Story:** 作为研究者，我要有一个独立的审查者盯着结论的可靠性，尤其是统计用法和引文，因为我自己容易漏。

#### Acceptance Criteria

1. 系统应在后台运行独立的 Reviewer，其运行不阻塞主对话。
2. 系统应强制 Reviewer 使用与被审查内容生成方不同供应商的模型；若仅有一家可用，则应明确告知这是降级状态。
3. 系统应在轮次结束、Artifact 保存、手稿编译前以及用户显式请求时触发审查。
4. 系统应支持的检查类别至少包括：证据、统计、可复现性、一致性、学术诚信。
5. 系统应区分 WARN 与 FAIL 两级严重度；WARN 不打断主 agent，FAIL 打断。
6. 系统应提供查询当前未关闭 findings 的接口，使 agent 在宣称完成前能自检 WARN 级发现。
7. 当 agent 声明已修复某条 finding 时，系统应将其标记为「已自报待复核」并在下一轮审查中确认或重新提出。
8. 系统应将每条 finding 关联到具体证据（Artifact、消息或 Claim），不接受无指向的泛泛发现。

---

### 需求 12：文献库

**User Story:** 作为研究者，我要平台帮我检索、去重、抓全文并管理参考文献，最后能直接导出投稿用的引用格式。

#### Acceptance Criteria

1. 系统应支持通过 DOI 解析文献元数据，来源至少覆盖 Crossref、OpenAlex、Semantic Scholar 与 PubMed。
2. 系统应按 DOI 精确匹配与标题模糊匹配对文献条目去重。
3. 系统应按开放获取优先的顺序尝试抓取全文，并在成功后将全文存为 Artifact 并与文献条目绑定。
4. 当全文来自 PubMed Central 时，系统应一并下载随文图像并使其可被读取。
5. 系统应支持导出 BibTeX 与 CSL-JSON。
6. 若某文献无法获取全文，则系统应记录已尝试的来源与失败原因，不得静默跳过。

---

### 需求 13：Claim Ledger 与手稿编译

**User Story:** 作为研究者，我最怕 AI 自信地编造数字和引文。我要手稿里每一条可核查的断言都能指向它的证据。

#### Acceptance Criteria

1. 系统应从手稿中识别可核查断言，至少覆盖数值结论、比较陈述、因果陈述与引文支撑陈述。
2. 系统应要求每条断言绑定至少一条证据，证据类型包括 Artifact 版本、DOI 与可复现的计算单元。
3. 当断言处于未关闭状态且无任何证据绑定时，Reviewer 应提出 FAIL 级发现。
4. 系统应记录每条证据的核验结论与执行核验的模型标识。
5. 系统应支持将结构化手稿编译为目标期刊格式，处理引用样式、字数限制与图表编号规范。
6. 系统应支持生成双盲送审版，按结构化元数据移除作者、机构、致谢与基金号。
7. 系统应检测自引造成的身份泄露（正文的自我指代引用且该引用作者与本文作者有交集）并提出发现。
8. 系统应明确告知用户双盲处理基于结构化元数据，对正文中的隐式身份线索不作保证。
9. 当引文核实任务执行时，系统应禁止模型凭记忆作答，必须经由检索工具取证。

---

### 需求 14：连接器与远程算力

**User Story:** 作为研究者，我要把外部数据库、工具服务和实验室集群接进来，在一个地方完成工作。

#### Acceptance Criteria

1. 系统应实现 MCP 客户端，支持 stdio 与 HTTP/SSE 两种传输。
2. 系统应仅在控制面 REPL 内核暴露 MCP 调用表面，Python 与 R 内核不得具备 MCP 通道。
3. 系统应支持三类算力目标：本地（含 GPU）、SSH 远程（含 Slurm/PBS 作业提交）、用户自带云算力。
4. 系统应对远程命令执行与算力作业提交施加用户审批门控。
5. 系统应为每个算力目标维护一份跨项目共享的环境笔记，内容限于该环境自身的知识（分区、账户、文件系统布局、环境激活方式、调度器行为），不得写入项目内容或分析结果。
6. 系统应支持查询当前会话可用的算力目标，并在用户中途新增后无需重启即可发现。
7. 当远程作业提交后，系统应跟踪其状态直到终止态，并将结果关联回发起会话。

---

### 需求 15：环境与包管理

**User Story:** 作为研究者，我要平台能为不同分析建不同环境，也能直接用我现成的项目 venv，而不是逼我把所有包塞进一个环境。

#### Acceptance Criteria

1. 系统应支持列出、创建与删除平台托管的 conda 环境。
2. 系统应支持注册用户既有的 venv，使内核直接从该 venv 启动且代码编辑可持久生效。
3. 系统应默认使用最快可用的包安装器，并在其不可用时回退。
4. 系统应在托管环境的包管理中避免混用 conda 与 pip 安装同一科学计算依赖，以防版本约束冲突导致运行时导入失败。
5. 当安装或卸载导致内核需要重启时，系统应明确告知内存状态将丢失，工作区文件不受影响。
6. 系统应支持将耗时的环境创建与包安装作为后台任务执行。
7. 系统应将 R 运行时置于独立环境，使 R 侧依赖变更不影响 Python 内核环境。

### 需求 16：记忆

**User Story:** 作为研究者，我不想每开一个会话就重新交代一遍项目背景和我的偏好。

#### Acceptance Criteria

1. 系统应支持三层记忆作用域：全局、项目、算力目标。
2. 系统应要求写入记忆时附带理由。
3. 系统应允许用户查看、编辑与删除全部记忆条目。
4. 系统不应将会话中的一次性细节写入长期记忆。

---

### 需求 17：审批与用户交互

**User Story:** 作为研究者，我要在有风险或有歧义的时候被问一句，而不是事后才发现平台替我做了决定。

#### Acceptance Criteria

1. 系统应在以下操作前发起用户审批：Artifact 删除、宿主路径授权、远程命令执行、算力凭据使用、域名白名单新增。
2. 系统应在审批卡片中说明将要发生什么、影响范围以及是否可逆。
3. 当用户拒绝某项审批时，系统不得对同一请求重试，应转而询问用户或改走其他路径。
4. 系统应支持 agent 在信息不足时向用户提问，并区分一般性提问与算力配置类提问。
5. 系统应支持授权的作用域与有效期设置，并允许随时撤销。

---

### 需求 18：成本与可观测性

**User Story:** 作为研究者，我要知道钱花在哪了、哪个模型慢、哪一步失败了。

#### Acceptance Criteria

1. 系统应记录每次模型调用的供应商、模型、输入输出 token、成本、延迟与结果状态。
2. 系统应按会话与按项目汇总成本，并支持按时间区间查询。
3. 当请求失败时，系统应记录失败类别与错误信息，供降级链分析使用。
4. 系统应在 UI 上展示当前轮次的累计用量。
5. 系统不应在可观测性数据中留存凭据或完整请求正文。

---

### 需求 19：数据完整性与迁移

**User Story:** 作为研究者，我的历史工作不能因为一次升级而损坏或静默变形。

#### Acceptance Criteria

1. 系统应以顺序编号的迁移管理数据库结构变更，并记录每条迁移的校验和。
2. 当已应用迁移的内容与记录的校验和不一致时，系统应拒绝继续并报错，不得尝试自动修复。
3. 系统应在单个事务内应用每条迁移，失败时完整回滚。
4. 系统应启用外键约束，并保证级联删除不留孤立记录。
5. 系统应保证重复执行迁移是幂等的。
6. 若运行时资产损坏或迁移记录与实际结构矛盾，则系统应给出可执行的修复指引而非静默继续。

### 需求 20：非功能需求

#### 20.1 零编译约束

1. 系统的运行时依赖不得包含需要在目标机器上现场编译的原生模块；所有原生依赖必须提供预编译二进制。
2. 系统应提供自动化检查，在依赖树中出现需现场编译的包时使构建失败。
3. 当依赖的预编译产物未随安装落盘时，系统应在安装阶段以幂等方式补齐，而非留到运行时报错。

#### 20.2 可靠性

1. UI 进程崩溃不应中断正在运行的长任务。
2. 控制平面应可独立重启，重启后恢复未完成的后台任务状态。
3. 系统退出时不应留下孤儿子进程。

#### 20.3 性能

1. 会话历史的加载应支持增量，长会话不得因一次性加载全部消息而阻塞 UI。
2. 数据库应启用 WAL，使长时间写入不阻塞 UI 的读取。
3. 大体积内核输出应通过旁路文件通道传递，不得整体塞入消息流。

#### 20.4 可移植性

1. 平台的路径、shell 与环境处理应集中在可替换的抽象层，为后续支持 Linux 与 macOS 留出空间。
2. 系统应允许通过环境变量覆盖数据目录位置，以支持测试与多实例并行。

#### 20.5 本地化与可访问性

1. 界面文案与模型输出的默认语言应为简体中文，同时支持中英混排的学术内容。
2. 交互控件应可用键盘完整操作，并具备可被屏幕阅读器识别的语义标签与状态。
3. 配色应满足正文与界面元素的对比度要求。

#### 20.6 隐私与遥测

1. 系统不应向任何第三方发送遥测或使用统计。
2. 系统的全部状态应保存在本机，不依赖云端后端。
3. 技能检索索引的构建与查询应在本地完成，不产生外部网络请求。
