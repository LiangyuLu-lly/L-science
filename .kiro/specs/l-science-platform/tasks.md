# L-science 实施计划

任务按分期路线组织。每条任务标注它满足的需求编号（对应 `requirements.md`）。

约定：

- 每条任务都必须以「可运行、可验证」结束，不留半成品接口。
- 原生依赖一律用 prebuilt，禁止引入需要 node-gyp 现场编译的包（需求 20.1）。
- 后端包的相对导入写 `.js` 后缀；UI 包走 bundler 解析用无扩展名。
- 新增或修改行为时同步补测试，测试与实现在同一条任务内完成。

- [x] 2.1 定义 IPC 契约与错误信封

- [x] 2.2 后端传输层与请求分发

### 4. Jupyter 内核客户端

- [x] 4.1 消息编解码
  - 把已有的 `signMessage` / `verifyMessage` 扩展为完整的帧编解码：多段帧的组装与解析、`<IDS|MSG>` 定位、原始帧字节用于签名校验（不能用重序列化后的 JSON 校验）
  - 测试：往返编解码等价；篡改任一段导致校验失败；空 key 时跳过校验
  - _需求：3.2_
  - 校验入站签名用**原始字节**而非 JSON 重序列化结果：键序或空白的任何差异都会让校验失败，症状是「内核消息被无声丢弃」
  - 签名无效时标记 `signatureValid: false` 交调用方丢弃，而不是抛异常——抛异常会让接收泵中断，后续输出全丢
  - 分段定位靠查找 `<IDS|MSG>` 而非固定下标：iopub 的 SUB 消息带 topic 前缀，DEALER 消息带 routing id
  - 测试：31 条，含「校验用原始字节」的专项断言
  - _需求：3.2_
- [x] 4.2 五通道 Socket 管理
  - shell / control / stdin 用 Dealer，iopub 用 Subscriber，hb 用 Dealer；全部绑定回环
  - shell 与 control 各跑一个接收循环，按 `parent_header.msg_id` 派发回复，支持多个在途请求
  - 心跳用 REQ 分帧形式 `[空帧, 载荷]`：ipykernel 的 hb 是 ROUTER，IRkernel 的是 REP，REP 要求空分隔帧开头，发裸单帧会被静默丢弃（表现为「R 内核心跳永远不可达」）
  - stdin 收到 `input_request` 时回空值：不回会让内核永久阻塞，表现为「cell 永远不结束」
  - _需求：3.3_
- [x] 4.3 执行请求与 iopub 关联
  - `execute_request` 发出后按 `parent_header.msg_id` 收集 iopub 输出直到该请求 `status=idle`
  - `sendRequest` **同步**返回 msg_id：若等 `await send()` 之后才知道 id，快内核可能已把输出推完，那些消息会被过滤器当作「不是我的」而永久丢弃
  - 输出队列有上界，超限丢弃并计数（一个 `while True: print()` 能以远超消费速度产出消息）
  - _需求：3.4_
- [x] 4.4 富输出解析
  - `stream` / `execute_result` / `display_data` / `update_display_data` / `clear_output` / `error` / `status` / `execute_input` 归一化
  - comm 类消息属 widget 协议，M1 显式忽略
  - 实测确认：Python 的 DataFrame 给 `text/plain` + `text/html`；R 的 data.frame 还额外给 `text/markdown` + `text/latex`（对论文直接有用）
  - _需求：3.6、3.8_
- [x] 4.5 内核启动与初始化序列
  - 就绪判定靠**反复发 `kernel_info_request` 直到有回复**，而非固定 sleep；同时监视子进程退出，启动失败立刻报错而不耗完超时预算
  - Python 初始化注入 `%matplotlib inline`（裸 ipykernel 不把 figure 渲染成 PNG）
  - R 必须注入 `R_HOME` 与 conda 环境的 DLL 目录；IRkernel 启动器在运行时写入内核目录，不依赖源码布局
  - 不使用 `conda run`：它在内核外多包一层进程，导致拿不到真实 pid，中断与强杀失效
  - 连接文件含 HMAC key，用完即删；`ports` 访问器只暴露端口不暴露 key
  - _需求：3.1、3.5、15.7_
- [x] 4.6 中断、重启与心跳
  - **Windows 上消息式中断不可能生效**：ipykernel 的 `_send_interrupt_children()` 对 `os.name == "nt"` 直接记录 "Interrupt message not supported on Windows" 后返回。因此 `interrupt()` 先发 `interrupt_request`，再检查执行是否真的停下，未停则重启并如实报告状态已丢失，返回值区分 `interrupted` / `restarted`
  - 重启为完整重建进程，语义比 `shutdown_request(restart=true)` 更确定
  - 重启与关闭必须强制收尾在途执行：通道一关 iopub 监听器随之消失，输出队列永不结束，调用方的 `for await` 会永久挂住
  - 重启期间通道断开，`execute()` 先 `await ready()` 而不是把「内核尚未就绪」抛给无从知晓后台重启的调用方
  - 初始化代码走内部路径，不占用户执行槽位——否则用户在重启完成前的下一次调用会撞上「已有执行在途」
  - 心跳在内核忙时仍可达，这正是它存在的理由（那时 shell 被占住，`kernel_info_request` 无法区分「在算」与「死了」）
  - _需求：3.9、3.10_
- [x] 4.7 内核池
  - 按 (会话, 语言) 复用；同一 key 的并发 acquire 共享一次启动，不会起出两个内核
  - 缓存内核已死时就地替换（进程可能被外部强杀）
  - 空闲回收跳过 busy 的内核，避免杀掉正在跑的长任务
  - 每个会话有独立工作目录，同名文件不互相覆盖
  - 语言环境缺失时抛出**含具体 conda 命令**的错误，而不是模糊报错
  - _需求：3.7_
- [x] 4.8 补全与内省
  - `complete_request` / `inspect_request`，均先 `await ready()`
  - _需求：3.12_

### 5. 沙箱后端

- [x] 5.0 经 FFI 获取 Windows 原生能力（AD-8，计划外但必须先做）
  - 用 `koffi`（自带 prebuilt，无需本机 C 工具链）调 Windows API，拿到两样没有原生调用就做不到的能力
  - **Job Object**：内核级内存限额 + `KILL_ON_JOB_CLOSE`。没有它限额只能退化为轮询（存在超限窗口），孤儿清理只能靠 `taskkill /T`（进程脱离父级就杀不到）
  - **内核中断事件**（`JPY_INTERRUPT_EVENT`）：没有它中断只能退化为重启，用户变量全丢
  - 实测：96MB 限额下超限进程被内核终止；`SetEvent` 在约 1.1-1.6 秒内产生真实 `KeyboardInterrupt` 且**状态完整保留**
  - FFI 只存在于 core 的 `win32/`；kernel 包通过注入的 `KernelInterrupter` 接口拿到能力，本身不依赖 FFI
  - 不可用时优雅降级并由 `nativeCapabilities().notes` 说明后果——「以为设了限额其实没设」比「知道没有限额」危险
  - 修正了 `interrupt()` 的一个真 race：原先轮询全局 `#executing`，用户中断后立刻跑下一个 cell 会让它误判为中断无效而重启内核；改为按具体那次执行的标识判断
  - 记录固有边界：单个长阻塞调用（`time.sleep(60)`）无法被 `interrupt_main()` 中断，此时如实退化为重启
  - _需求：5.2、3.9_

- [x] 13.1 文献元数据解析与去重
  - Crossref / OpenAlex / Semantic Scholar / PubMed / Europe PMC / arXiv **六家并行**后按完备度合并，而不是依次尝试取第一个成功：串行最坏是六个 20s 超时叠成两分钟；取第一个会让记录质量取决于谁先响应（随机），同一个 DOI 两次入库可能一次有摘要一次没有
  - 去重分**三档**（same / likely / distinct），两个不同 DOI **永不自动合并**：preprint 与正式版是两个真实注册对象，合并掉一个之后「当初引的是 preprint」这件事无法恢复。likely 只提示不动手

- [x] 14.2 算力目标管理
  - SSH 走**系统的 `ssh` 二进制**，不引 JS SSH 库：实验室集群的接入方式几乎从不是「主机名 + 端口 + 私钥」——跳板机、按主机匹配的私钥、ssh-agent、硬件密钥这些用户在 `~/.ssh/config` 里早就配好了。引库等于重新实现一遍，而实现不全的表现是「终端里能连上、平台里连不上，且看不出为什么」。用系统 ssh 的规则很好解释：**你在终端能上去，平台就能上去**。附带好处是不引 native 依赖
  - 三条不能改的 ssh 选项：`BatchMode=yes`（不加则需要交互时永久挂住等一个不存在的 TTY）、`StrictHostKeyChecking=yes`（`no` 与 `accept-new` 都等于对中间人不设防）、`PasswordAuthentication=no`（不排除时报的是含糊的 `Permission denied (publickey,password)`，排除后报的是「没有可用的公钥」——那才是用户要看到的）。用户自定义选项过白名单：一个 `-o StrictHostKeyChecking=no` 就能把最重要的一条撤掉，而配置里多一行谁都不会注意到
  - 主机公钥**分三步**（ssh-keyscan 取回 → 审批卡片展示指纹 → 写 known_hosts）：首次连接自动信任恰好是中间人唯一需要的窗口。指纹变了时平台**不覆盖**，报出来让人分辨——那要么是主机重装了系统，要么就是中间人
  - 远程命令一律 **base64 传输**：ssh 把 argv 拼成一个字符串交给远端登录 shell 解析，引号、`$`、反引号、换行都会被二次解释，而作业脚本里这些是常态。任何「小心加引号」的方案都会在某个字符组合上破功，而破功的表现是命令被截断成一半后执行
  - **危险度分三档，破坏性命令不受持久授权约束**：每条命令都弹卡片行不通（一次排查跑十几条 `ls`，弹十几张卡片的结果是用户给出 always 授权，而那个授权同时放行了 `rm -rf`）。因此只读在有授权时直接放行、写命令问一次、破坏性命令**先不查授权**每次单独问——查了就会命中那条为了不被 `ls` 烦到而给的 always，而这正是分档存在的唯一理由。判不出来的一律算写而不是只读（两个方向的错误代价不对称：多一次点击 vs 数据没了）
  - 作业状态里 **`lost`（结果不明）是独立一档**：调度器不再报告而历史记录拿不到时，结果不明。并进 `completed` 会让用户去读一份没写出来的输出；并进 `failed` 会让他排查一个可能没发生的失败。状态查询一次往返同时问队列与历史记录——分两次的话两次之间作业刚好结束会得到一个假的「不明」
  - PBS 的 `F` 状态不区分成败，必须看 `Exit_status`；只看 `job_state` 会把每个失败的作业报成已完成。PBS 的资源请求拼成一行 `-l select=`，分开写在 PBS Pro 上互相覆盖且不报错
  - 跟踪用**轮询**而非长连接：合盖、换网、VPN 重连都会断掉连接而作业还在跑，而重连后第一件事恰好就是「问一下现在什么状态」。间隔按作业时长退避（10s → 5min），连续失败时指数退避但有上限——超过它等于放弃跟踪。进程重启后 `resume()` 接上（需求 14.7 的「跟踪到终止态」不能因为用户关过一次窗口就作废）
  - BYOC **不绑任何一家云的 SDK**：绑了就把「自带云算力」变成「自带我们支持的那家云」。改成三条命令模板 + 状态映射，覆盖面是任何有 CLI 或能用 curl 提交作业的平台。映射不到的状态记成 `lost` 而不猜
  - 目标与授权在应用库（一台集群是研究者的基础设施，不属于某个项目），作业与命令审计在项目库（需求 14.7 要求结果关联回会话，而会话在项目库）。登记**不在模型面也不在控制面**：它需要主机名、跳板机与分区这些只有用户知道的事实，模型会填出看起来合理的值而失败要等探测时才出现

- [x] 14.4 环境与包管理工具
  - **conda / pip 混装门**是这一组的核心（需求 15.4）。需求里那句「防版本约束冲突导致导入失败」，实际发生的事更具体：conda 的 numpy 链接环境里那份 MKL/OpenBLAS，PyPI 的 wheel 自带一份，两份都在一个进程里时符号来自哪一份取决于加载顺序，结果是 ImportError（最好的一种，至少报错了）、进程崩、或者**算出错误的数值而完全不报错**。第三种是这道门真正要防的：它的代价不是「程序挂了」，是「结论错了而没人知道」
  - 判定按**共享的原生库分组**而不是按包名：只比对同名包会漏掉最常见的一类——conda 装了 scipy，然后 pip 装 numpy，包名不同但冲突照样成立。九个组（BLAS、HDF5、LLVM、Arrow、地理空间、CUDA、OpenCV、Qt、神经影像），每组写明共享哪个原生库与混装后的具体表现。只收**链接原生库**的包：纯 Python 包混装不会有这个问题，列进来只会让这道门在无害的情况下反复挡人，而那会让用户去找绕过它的办法
  - 权威来源是**探测而不是我们的安装记录**：`conda list --json` 把 pip 装的包标成 `channel: "pypi"`。用户可以在环境里自己跑 pip，那时我们的记录会漏而 conda 不会。conda list 不可用时退回 pip list 会让所有包看起来都是 pypi 装的（检查永远不触发），因此那种情况要在探测结果里显式报出来
  - 正面表达也做了：conda 环境里对原生库敏感的包**默认走 conda 家族**。不只是挡住混装，还要让默认选择本身不产生混装。另外提供「现在已经混着了吗」——用户最常见的求助是「我的 numpy 导入报 DLL 错误」，而那时混装已经发生了
  - **安装器回退只在家族内**（需求 15.3）：`uv > pip`、`micromamba > mamba > conda`。让 uv 顶替 conda 不是回退，是换了包来源——那正是 15.4 要防的事。因此 `pickInstaller` 的 family 参数必填，没有「随便给我一个最快的」这种调用方式
  - 每个安装器锁定目标环境的方式都不同，而这是最容易出错的地方：pip 用 `<interpreter> -m pip`（PATH 里的 pip.exe 属于哪个环境取决于 PATH 顺序，装错的表现是「装成功了但导入不到」）；uv 必须给 `--python`；conda 家族用 `--prefix` 而不是 `-n`。R 包必须显式给 `repos`，不给的话 R 会弹图形化镜像选择器而我们没有 TTY——与 ssh 的 BatchMode 同一类问题
  - 包名过白名单式校验，拒绝以 `-` 开头：我们用 execFile 传 argv 所以 shell 元字符无害，但 `--index-url` 会被安装器自己接受，而一个指向攻击者服务器的 index-url 能让 `pip install numpy` 装进任意代码
  - 内核**直接从用户的 venv 启动**（需求 15.2）：`KernelPool` 加 `pythonEnv`/`rEnv` 覆盖回调，每次启动现取。「代码编辑可持久生效」靠**不复制任何东西**实现——任何把环境复制一份的做法都会让 `pip install -e` 装的可编辑包与直接改的源码不再生效，而那个失败的表现是「我改了代码但跑的还是旧的」。`PoolEntryInfo` 记下 `envPrefix`：按「当前默认环境」事后推断会把切换默认之前起的内核算到新环境头上，于是「装包要不要重启」答错，而错的方向是清掉一批本来不受影响的内存状态
  - 缺 ipykernel 时**照样登记**但状态标 incomplete：拒绝登记会让用户陷在死循环里（要先装 ipykernel 才能登记，而装它最方便的方式正是登记之后用平台的包管理）
  - 托管与登记的区别决定**能不能删目录**：`managed` 删目录 + 删记录；`registered` 只删记录（那个目录里可能有他花了一天装好的 GDAL）。判据是名字而不是类型——用户自己的 conda 环境也是 conda 环境，判错的方向是把他的 research-env 标成 managed 然后他点了「删除」。conda remove 失败时**不回退到 rm -rf**

- [x] 14.5 其余审批类型
  - 需求 17.1 点名的五类此前已全部有门（制品删除、宿主路径、远程命令、算力凭据、域名白名单），因此这一项做的是把机制的三个缺口补上
  - **装包缺一道门** → 新增 `package-install`。需求 17.1 没点名它，但它属于同一类：`pip install` 会执行包自带的构建脚本，也就是任意代码执行，在用户自己的机器上、用他的权限。第二个理由是影响范围——装包改动的是环境，而环境被此后所有会话的内核共用。卡片给出命令原文（用户能判断的是命令，不是「安装 3 个包」）、明说这是任意代码执行、标 `reversible: false`（装错的包可以卸，但构建脚本已经跑过了）。作用域最宽到 project：环境是全局资源，一条 always 等于把所有项目的环境都交出去了。审批门排在混装检查**之后**——让用户为一个注定被拒的请求点一次同意是纯粹的骚扰
  - **有效期此前是死代码** → `SCOPE_DURATION_MS` 里除 once 外全是 null，`expiresAt` 恒为 null，而两个 grants repo 的 check 都会看它。现在 `ApprovalRequest` 加 `expiryOptions`、`decide` 加 `expiresInMs`。与作用域分成两个字段：作用域回答「在哪些上下文里生效」，有效期回答「生效多久」，合成一个下拉框会让选项数量变成两者的乘积
  - `always` 的默认从永久改成 **90 天**：这是最宽的一档，而用户按下它时想的通常是「这段时间我都在弄这个」，不是「余生都同意」。给一个到期日意味着这条授权会被重新审视一次，而重新审视是这类宽授权唯一的安全阀。想永久的人可以显式选「不过期」——那是他明确的意思，与默认落到永久不是一回事。卡片上有效期默认取**最短**档位，与作用域默认取最保守同理
  - **审批审计没有出口** → `ApprovalRepo` 的文件头一直写着「落盘的目的是留审计痕迹」，但「谁在什么时候批准了删除哪个制品」在库里有答案而界面上问不出来，那等于没有审计。新增 `approval.pending`（重开窗口后恢复显示——没有它的话一次刷新就让用户看不到正在等他决定的卡片而后端仍在挂着）与 `approval.history`（带上**当时给用户看的内容**：只记 kind 与 state 的话，事后无法判断那次同意是基于完整说明还是含糊提示）
  - 历史里区分「历史上被拒过」与「**现在还在拦截**」：库里的 denied 行是历史，拒绝记忆是进程内的那份。用户看到一条三天前的拒绝记录时，他想知道的是「现在还挡着吗」
  - **拒绝记忆可撤销** → 需求 17.3 要求拒绝后不得重试，而这条规则在用户改主意时会挡住他自己：他明确说「现在可以了」，系统仍然直接拒绝且不给被询问的机会，此前唯一的办法是重启后端。按 id 而不是按 payload 撤销——界面上他看到的是一条历史记录，从那条记录反推 payload 要求 UI 复制一份指纹逻辑
  - 装包被拒用 `policy_denied` 而不是 `bad_request`：混在一起会让前端把「用户拒绝了」显示成「参数有问题」，于是他看到一条建议他改参数的提示，而他刚刚做的正是拒绝。模型面三种失败三个错误名，因为三者对的下一步完全不同
  - _需求：17.1、17.5_
